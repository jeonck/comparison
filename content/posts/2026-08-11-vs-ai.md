## Overview

여러 메신저 채널에 AI 에이전트를 연결할 때, 하나의 중앙 프로세스가 모든 채널을 중계하는 <strong class="kw">게이트웨이</strong> 방식과 채널별로 봇을 따로 만들어 각각 AI API를 호출하는 <strong class="kw">개별 통합</strong> 방식 중 하나를 선택하게 된다. 게이트웨이는 로컬 머신이나 서버에서 텔레그램·디스코드·슬랙·웹 채팅 등을 하나의 라우팅 계층으로 묶어 인증과 로직을 한 곳에서 관리하는 반면, 개별 통합은 채널마다 별도의 배포와 자격 증명을 필요로 한다. 두 방식은 신규 채널 추가 속도, 장애 격리 범위, 운영 부담에서 뚜렷한 차이를 만든다.

## Comparison Table

| 구분 | 멀티채널 게이트웨이 | 개별 채널 봇 |
| --- | --- | --- |
| 핵심 구조 | 단일 프로세스/서버가 모든 채널 어댑터를 관리하며 AI 에이전트로 라우팅 | 채널마다 독립된 봇 프로세스가 각자 AI API를 직접 호출 |
| 메시지 수신 | 게이트웨이가 각 플랫폼의 Webhook/폴링을 통합 수신 후 내부 큐로 전달 | 각 봇이 자신의 플랫폼 SDK로 메시지를 직접 수신 |
| 포맷 정규화 | 텔레그램 Update, 디스코드 Interaction 등 서로 다른 포맷을 공통 스키마로 변환 | 각 봇이 자기 플랫폼 포맷을 그대로 프롬프트로 변환, 로직 중복 발생 |
| 인증/자격 증명 관리 | API 키와 토큰을 게이트웨이 한 곳에서 중앙 관리 | 채널 수만큼 자격 증명을 각 배포본에 개별 관리 |
| 신규 채널 확장 | 어댑터 모듈만 추가하면 기존 라우팅·AI 연동 로직 재사용 | 신규 채널마다 봇을 처음부터 새로 구축 |
| 장애 영향 범위 | 게이트웨이 다운 시 연결된 전체 채널이 동시에 마비 | 한 채널 봇의 장애가 다른 채널에 영향을 주지 않음 |
| 운영·배포 부담 | 프로세스/서버 1개만 모니터링하면 되어 운영 단순 | 채널 수만큼 배포 파이프라인과 모니터링을 각각 유지 |

## Key Differences

- 게이트웨이는 모든 채널 트래픽이 한 지점을 통과하는 <strong class="kw">단일 장애점</strong> 구조인 반면, 개별 봇은 장애가 채널 단위로 격리된다.
- 인증 정보는 게이트웨이에서 <strong class="kw">중앙 관리</strong>되지만, 개별 통합에서는 채널마다 흩어져 관리 부담이 커진다.
- 신규 채널 추가 시 게이트웨이는 <strong class="kw">어댑터 하나</strong>만 붙이면 되지만, 개별 통합은 봇을 통째로 새로 만들어야 한다.
- 메시지 포맷 정규화 로직은 게이트웨이 방식에서 <strong class="kw">한 번만</strong> 구현되고 재사용되며, 개별 통합에서는 채널마다 반복 구현된다.

## When to Use Each

**멀티채널 게이트웨이**

- **여러 메신저를 동시에 운영**: 텔레그램, 디스코드, 슬랙, 웹 채팅을 동일한 AI 에이전트로 응답시켜야 할 때 라우팅 로직을 한 곳에 모을 수 있다.
- **로컬/자체 서버 운영**: 사용자가 직접 서버나 로컬 머신에서 구동하며 API 키와 세션을 외부에 노출하지 않고 중앙에서 통제하고 싶을 때 적합하다.
- **빠른 신규 채널 추가**: 서비스 확장 시 어댑터만 추가해 기존 인증·AI 연동 로직을 그대로 재사용할 수 있다.

**개별 채널 봇**

- **단일 채널에 집중**: 예를 들어 슬랙 워크스페이스 하나에만 봇을 배포한다면 별도 게이트웨이 계층 없이 플랫폼 SDK로 직접 구현하는 편이 더 단순하다.
- **채널별 장애 격리가 중요할 때**: 한 채널의 장애나 배포 실수가 다른 채널 서비스에 영향을 주지 않아야 하는 경우 독립 배포가 유리하다.
- **플랫폼별 특화 기능 활용**: 슬래시 커맨드, 버튼, 스레드 등 특정 플랫폼 고유 UI를 깊게 활용해야 할 때는 공통 스키마로 추상화하지 않는 편이 구현이 쉽다.
